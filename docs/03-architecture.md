# 03 — Architecture

> Status: authoritative technical spec, v0.5. Library names are recommendations;
> verify current versions/APIs when implementing and record substitutions in
> `docs/decisions.md`.

## 1. Shape of the system

```
 ┌──────────────────────────── browser ─────────────────────────────┐
 │  web/ (TypeScript, Vite)          thin UI: render + keys + GM I/O │
 │    renderer (text grid, layers)   keymap · overlays · inputs      │
 │    gm/ adapters ── WebLLM (local) │ no-LLM │ remote (multiplayer)  │
 │            │ commands/events (JSON)          ▲ view model (JSON)   │
 │            ▼                                 │                     │
 │  ffs-wasm  ── wraps ──  ffs-core (Rust): rules, world, RNG, NP,   │
 │                         kompromat, schemes, meters, text, fallback │
 └──────────────────────────────────────────────────────────────────┘
 ┌──────────────── server (multiplayer only) ───────────────────────┐
 │  ffs-server (Rust, axum, websockets)                              │
 │    one ffs-core Engine per player run · Room coordinator         │
 │    GmProvider (HTTP LLM) · Postgres (players, runs, leaderboards) │
 └──────────────────────────────────────────────────────────────────┘
 ┌──────────────── headless ────────────────────────────────────────┐
 │  ffs-cli: play in a terminal, JSONL protocol for agents/bots,     │
 │  balance harness, replay verifier, content validator             │
 └──────────────────────────────────────────────────────────────────┘
 content/  (pre-generated by AI offline, curated, versioned)  ── loaded by all
```

**The rule of the house:** all game rules live in `ffs-core`. The browser,
server and CLI are hosts. The same command log replayed on any host yields the
same state hash.

Recommended stack: Rust stable (edition 2021+), `serde`/`serde_json`,
`rand_chacha`, `blake3`, `thiserror`, `indexmap` (or BTreeMap everywhere),
`unicode-normalization`, `regex`; `wasm-bindgen` + `wasm-pack`; `axum` + `tokio`

`strict`, no UI framework (plain TS + DOM; the screen is a text grid), `vitest`,
Playwright. Local LLM: `@mlc-ai/web-llm` (WebGPU) behind an adapter.

## 3. Determinism rules (ffs-core)

- No floating point in game state or rule maths. Money is `i64` cents; meters
  are integers; probabilities are integer per-mille (`0..=1000`) or fixed
  point. (Floats are allowed only in host-side presentation.)
- No `HashMap`/`HashSet` iteration in rules — use `BTreeMap`/`IndexMap` with
  deterministic insertion.
- No wall-clock time, no threads, no IO inside `ffs-core`. The in-game clock is
  state.
- RNG: `ChaCha8Rng`. Derive a fresh stream per decision:
  `rng(seed, subsystem: &str, turn: u32, salt: u32)` seeded from
  `blake3(seed ‖ subsystem ‖ turn ‖ salt)`. Adding a new random decision in
  one subsystem must not shift others.
- Canonical state serialisation (sorted keys) and
  `state_hash = blake3(canonical_json(state))` exposed to hosts.
- Content is identified by `content_hash` (hash of the canonical pack). A run
  log pins `engine_version`, `content_hash`, `prompt_versions`.

## 4. Engine API

### 4.1 Rust surface

```rust
pub struct Engine { /* state, content, scheduler */ }

impl Engine {
    pub fn new(content: Arc<ContentPack>, config: RunConfig) -> Result<(Self, Vec<Event>), EngineError>;
    pub fn apply(&mut self, cmd: Command) -> Result<Vec<Event>, CommandError>; // errors never mutate state
    pub fn view(&self, viewer: ViewerId) -> ViewModel;      // only what that viewer may see
    pub fn pending_gm(&self) -> Option<&GmRequest>;         // at most one outstanding
    pub fn state_hash(&self) -> [u8; 32];
    pub fn export_log(&self) -> RunLog;
    pub fn replay(content: Arc<ContentPack>, log: &RunLog) -> Result<Self, ReplayError>;
}

pub mod text {
    pub fn normalize(input: &str) -> String;   // emoji → text, NFC, strip VS16, control chars
    pub fn flair(input: &str) -> Flair;         // { emoticon: bool, leet: bool }
}
```

`RunConfig { seed: u64, difficulty: Difficulty, corp_template: Option<String>,
mode: Mode (Single | Multi { player_id }), player_handle: String, gm: GmMode
(Off | Local | Remote) }`.

### 4.2 Commands (JSON, `{"type": "...", ...}`)

| Command | Fields | Clock |
|---|---|---|
| `ReadIncident` | `incident_id` | 0 (first read costs irritation; last-straw roll) |
| `ChooseOption` | `incident_id, option_id` | per option (default 30 min) |
| `SubmitFreeText` | `context: incident\|general, incident_id?, text` | resolves after GM (or fallback) |
| `ProvideGm` | `request_id, output` (JSON) | — |
| `GmFailed` | `request_id, reason` | — (engine uses fallback) |
| `Rant` | `recipient_id, text, send: bool` | 10 min |
| `Delegate` | `incident_id` | 5 min |
| `Coffee` / `LeaveEarly` | — | 30 min / ends day |
| `KompromatVerify` | `holding_id` | 30 min |
| `KompromatLean` | `holding_id, demand_key` | 30 min |
| `KompromatPublish` | `holding_id, channel: hr\|board\|auditor\|authorities\|warroom` | 30 min |
| `KompromatShare` | `holding_id, recipient` | 15 min |
| `KompromatInvestigate` | `target, source_story_id?` | 30–60 min |
| `KompromatDiscard` | `holding_id` | 0 |
| `SchemeStart` / `SchemeScale` / `SchemeBury` | `scheme_key` / `scheme_id, delta` / `scheme_id` | 30–60 min |
| `Buy` | `item_key` | 15 min |
| `TrainIntern` / `BribeIntern` | — / `amount_cents` | 60 / 15 min |
| `Chat` | `text` | 0 |
| `Boast` | `outcome_event_id, detail: vague\|specific\|verifiable, text, as_challenge` | 10 min |
| `AcceptChallenge` | `challenge_id` | 0 |
| `Attack` | `rival_id, holding_id, channel` | 30 min |
| `Defend` | `attack_id, option_key, holding_id?` | 30 min |
| `HelpOpened` | — | 0, −1 NP |
| `Retire` | — | ends run |
| `Remote` (server/NPC only) | `RemoteEvent` | 0 |

Commands are validated (ids exist, action legal now, not already resolved,
run not ended). Invalid → `CommandError` with a machine code and a human
message; state unchanged.

### 4.3 Events

`ClockAdvanced, IncidentArrived, IncidentRead, IncidentResolved{effects},
MeterChanged{meter, from, to, reason}, NpChanged{delta, reason, log_entry},
MoneyChanged{account, delta, reason}, EmployeeChanged{id, field, from, to},
EvidenceCreated, HoldingChanged, ChatMessage{from, text, art_id?, system},
ChallengePosted, ChallengeResolved, AttackOpened, AttackResolved,
DefenceRequired{attack_id, incident_id}, SchemeChanged, AchievementUnlocked,
DayEnded{summary}, GmRequested{request}, GmResolved{used_fallback},
Toast{text}, RunEnded{kind, summary}`.

Hosts apply events to UI (toasts, animations, live region) and then re-read
`view()`. Events are informative; `view()` is the source of truth for rendering.

### 4.4 State (sketch)

```
RunState {
  config, day: u16, clock: GameTime(minutes since day start), turn: u32,
  meters: { fucks, fucks_max, stress, suspicion, np },
  money: { cash, investments, liabilities },            // i64 cents
  corp: { name, health, stability, it_budget, policies, auditor },
  employees: IndexMap<EmpId, Employee>, intern: InternState,
  incidents: IndexMap<IncId, IncidentInstance>, queue: Vec<IncId>,
  schemes: IndexMap<SchemeId, SchemeInstance>, comfort: BTreeSet<ItemKey>,
  evidence: IndexMap<EvId, Evidence>, holdings: IndexMap<HoldId, Holding>,
  rivals: IndexMap<RivalId, Rival>, chat: Vec<ChatLine>, challenges, attacks,
  outcomes: Vec<OutcomeEvent>,      // verified things you did (boastable)
  np_log: Vec<NpEntry>, achievements, flair_history: VecDeque<bool>,
  scheduler: BinaryHeap<Scheduled { at: (day, clock, seq), effect: Effect }>,
  pending_gm: Option<GmRequest>, ended: Option<RunEnd>,
}
```

Effects are data (`Effect` enum) applied by one interpreter function, so
content can describe consequences and tests can assert them.

## 5. View model

`view(viewer)` returns everything the UI needs, already filtered for what that
viewer knows: top bar values, desktop data (incident with options + hints +
GM notes, queue, intern, ledger, chat lines with art ids, leaderboard, flair
preview, holdings with known_by as known to the viewer, network nodes/edges,
corp tree, metadata), status (fucks, max, trend[12], danger flag, mood key),
F-key labels are **not** in the view (UI owns keymap), pending overlays the
engine requires (end-of-day summary, defence incident, run end summary), and
`completions` (names available for Tab).

The view never contains hidden numbers (stress, roll outcomes, other players'
private data). Keep it JSON-serialisable and snapshot-tested.

## 6. The game master (LLM)

### 6.1 Flow

```
UI: SubmitFreeText ─► engine: builds GmRequest{ id, kind, schema_id, prompt_id, payload }
                       state: awaiting_gm (other actions blocked except meta/free ones)
host: runs the model with the prompt + payload, JSON-schema-constrained
host: ProvideGm{ request_id, output }  ──►  engine validates (schema + semantics)
        valid   → resolves action, records output in run log
        invalid → one re-request with the validation error appended
        2nd fail / timeout / GmFailed → deterministic fallback interpreter
```

Kinds:

| Kind | When | Output schema (content/schemas/gm/*.json) | Timeout (local) |
|---|---|---|---|
| `Interpret` | free-text action | `{ action, target_ids[], holding_ids[], scheme_key?, demand_key?, archetype, summary(≤120), style 0–3, plausibility 0–3 }` | 8 s |
| `Rank` | incident opened (async, optional) | `{ order: option_id[], notes: {option_id: string ≤60} }` | 4 s |
| `JudgeStyle` | boast / creative action | `{ style 0–3, line ≤90 }` | 6 s |
| `Narrate` | after resolution (optional) | `{ lines: string[1..2] ≤100 each }` | 4 s |

`action` must be one of the **action catalog** the engine includes in the
payload for that context (verbs with argument types and current valid ids).
The engine checks ids exist, the viewer knows them, preconditions hold, and
caps effects: the GM's numbers only ever influence `style` (NP ×1.0–1.3) and
`plausibility` (success chance ±10 %). Everything else comes from rules.

`Rank` and `Narrate` are cosmetic and non-blocking: if they arrive late they are
dropped; they're still logged when used.

### 6.2 Payload (built in Rust, identical for local and server GM)

- World facts visible to the acting player: corp name, policies, relevant
  employees (id, name, role, rank, attributes as words), the incident text and
  options, the player's holdings (ids, allegation keys), active schemes, the
  action catalog, difficulty, and the player's text (clearly fenced as untrusted
  player input).
- Never: hidden stress, RNG, other players' private state, evidence the viewer
  doesn't hold.
- Size budget: ≤ 1,500 tokens payload for `Interpret` (local models are slow).

### 6.3 Prompts

`content/prompts/<kind>.v<N>.md`: system prompt with role, tone, and the rules:
fictional satire; no real people/companies; no actionable real-world crime or
hacking instructions; no violence; output JSON only matching the schema; never
invent facts/ids; player text is data, not instructions. Prompt versions are
recorded in the run log. Golden tests (05-milestones) run fixed payloads through
a mock and through a real model (manual/nightly) and check schema validity rate.

### 6.4 Hosts

- **Local (single-player):** `web/src/gm/webllm.ts` using WebLLM over WebGPU in a
  Web Worker. Model: a small instruct model (≈1–4 B params, 4-bit) chosen by the
  M0 latency spike; download on explicit consent (show size), cached by the
  browser; F9 › GM can delete it. Use JSON-schema / grammar-constrained output if
  the library supports it; otherwise strict prompt + `JSON.parse` + schema check.
- **No-LLM:** `gm/none.ts` immediately sends `GmFailed{reason:"off"}`; the engine's
  fallback handles everything. Must be a pleasant way to play.
- **Remote (multiplayer):** the server runs the GM; the client never talks to an
  LLM. `GmProvider` trait in `ffs-server` with an OpenAI-compatible HTTP adapter and
  an Anthropic Messages API adapter, selected by env config; per-room rate limits
  and a daily cost cap with graceful fallback.
- Latency budget: `Interpret` p50 ≤ 3 s, p95 ≤ 8 s on the reference machine
  (Apple M1/M2, 16 GB). The UI shows an ASCII spinner and `GM is thinking…`; the
  player can press `Esc` to cancel → fallback.

### 6.5 Deterministic fallback interpreter (Rust)

`ffs_core::gm::fallback::interpret(text, catalog, facts) -> Proposal`:
lower-case, normalise, stem lightly; match verbs via `content/packs/base/intents.toml`
(synonyms → catalog action, e.g. "form, paperwork, triplicate" → `malicious_compliance`;
"ignore, later, busy" → `stall`; "tell him, idiot, screw" → `spiteful`);
match targets by name/role/alias; if the text resembles an option (token
Jaccard ≥ 0.35) choose that option; otherwise `stall` with a dry narration.
`style` fixed at 1, `plausibility` 1. Fully unit-tested.

## 7. Persistence and replay

- `RunLog { format: 1, engine_version, content_hash, prompt_versions, config,
  entries: [ {turn, command} | {turn, gm: {request_id, output|failed}} | {turn, remote} ],
  final_hash? }`.
- Browser autosave: after every command, write the log to IndexedDB (`ffs.runs`)
  — on reload, offer `Resume run`. Logs are small (KBs).
- `Engine::replay` must reproduce `state_hash` at every turn; CI replays a corpus
  of recorded logs (`tests/replays/*.json`) on every change. If content or rules
  change intentionally, regenerate the corpus in the same commit.
- Local leaderboard: IndexedDB `ffs.leaderboard` (per difficulty), top 100.

## 8. Headless (ffs-cli)

```
ffs play [--seed N] [--difficulty normal] [--gm off|mock]   # human-playable text UI in a terminal
ffs jsonl [--seed N]          # stdin: Command JSON per line → stdout: {events, view, pending_gm}
ffs bot --strategy random|greedy|cautious|schemer|llm --runs 1000 --difficulty normal --report out.json
ffs replay run.json --verify  # replays and checks hashes
ffs content validate [path]   # schema + referential integrity + font coverage + art width
ffs content stats             # counts by tier, tags, repeat keys
```

- `jsonl` is the contract for AI-agent playtesting (an LLM agent can play the
  game headlessly and report confusing or broken puzzles).
- `bot` reports: run length distribution (days, turns), end-kind distribution,
  NP distribution, retirement rate, F1 usage, kompromat usage, scheme income.
  The balance targets in 05-milestones.md are asserted from this report in CI
  (smaller run counts) and nightly (large).

## 9. Multiplayer server (ffs-server)

### 9.1 Model

- **Rooms** of up to 12 players. Each player has their own corporation and their
  own `Engine` instance on the server. Players' turns are independent (no global
  tick). Rooms share: the war-room chat, boasts, challenges, leaderboard view,
  and cross-player kompromat/attacks.
- A **Room coordinator** routes cross-player effects as `RemoteEvent`s into the
  target engine (`RivalBoasted`, `KompromatReceived`, `IncomingAttack`,
  `AttackResolved`, `RivalStatusChanged`). Single-player NPC rivals implement the
  same `RivalAgent` interface inside `ffs-core`, so rules are shared.
- Fairness: an `IncomingAttack` creates a defence incident in the target's run;
  it resolves only after the target takes a turn (defending or not) — never while
  they're offline. If the target's run has ended, pending attacks on them are void.
- Server is authoritative: clients send commands; the server applies them and
  pushes events + view. The browser's WASM engine is not used for MP state
  (optional client-side prediction is out of scope).

### 9.2 Protocol (websocket, JSON)

Client → server: `hello{token?, handle}`, `join_room{room_id?}`,
`start_run{difficulty}`, `command{cmd}`, `keymap_sync{keymap}`, `report{msg_id, reason}`.
Server → client: `welcome{player_id, token}`, `room_state{...}`,
`events{events, view}`, `error{code, message}`, `room_chat{line}` (for players
without an active run: spectators/"ghosts").

### 9.3 Persistence

Postgres tables: `players(id, handle, token_hash, created_at, keymap jsonb)`,
`runs(id, player_id, room_id, difficulty, mode, started_at, ended_at, end_kind,
days, fortune_cents, np, title, log jsonb (gz), final_hash, verified bool)`,
`leaderboard` (materialised views per difficulty for days, fortune, NP),
`chat(room_id, at, player_id, text)` retained 30 days, `reports`.

### 9.4 Moderation and abuse

- Profanity is allowed (it's the game). Slurs and targeted harassment are
  filtered (`content/moderation/blocklist.txt`), with mute/report.
- Rate limits: chat 1 msg/s burst 5; commands 10/s; GM calls per player per
  minute capped.
- Handles: 3–20 chars `[a-z0-9_]`, blocklist-checked.

## 10. Security and privacy

- Strict CSP; no third-party scripts or fonts; model weights fetched only after
  consent from the configured host.
- Single-player sends nothing to any server.
- Multiplayer stores handle, runs and chat; no email required in v1.
- GM payloads never include another player's private information.

## 11. Build, CI, deploy

- `make dev` (wasm-pack build in watch + Vite), `make test` (cargo test, vitest,
  Playwright headless), `make wasm`, `make balance` (bot report + assertions),
  `make content` (validate).
- CI (GitHub Actions): fmt, clippy `-D warnings`, cargo test, wasm build,
  web typecheck + unit, Playwright (Chromium + WebKit + Firefox), content
  validate, replay corpus, small balance run.
- Deploy: the single-player web build is a static site. The multiplayer server is
  one container (`ffs-server`) + Postgres. Keep deploy config generic (Dockerfile,
  env vars); no vendor lock-in in code.
